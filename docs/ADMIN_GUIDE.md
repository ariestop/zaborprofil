# Руководство администратора

На текущем этапе доступны:

- страница входа `/admin/login`;
- защищенный dashboard `/admin/dashboard`;
- страницы и блоки `/admin/pages`;
- структурированный builder страницы `/admin/pages/{id}/builder`;
- Media Library `/admin/media`: загрузка drag&drop с прогрессом и дедупликацией по хешу, поиск и фильтры, пагинация, alt/title/описание/папки, «где используется», удаление с подтверждением и защитой используемых файлов, variants для изображений (см. [admin/media-library](admin/media-library.md));
- управляемые меню `/admin/menu` для `header`, `footer`, `service`;
- CRM заявок `/admin/crm` (список с серверной пагинацией, поиск, фильтры, карточка `/admin/crm/{id}`, заметки, ответственный, экспорт CSV; см. [admin/crm-leads](admin/crm-leads.md));
- SEO-панель `/admin/seo`: редиректы, robots.txt, журнал 404 и SEO-аудит;
- настройки, health center, maintenance mode и audit log.

## Визуальный редактор блоков

В разделе `/admin/pages` для блоков `text` и `text_image` доступно два режима:

- `Визуально` — оператор работает с полями формы и форматированием текста, без ручного JSON;
- `JSON` — режим для продвинутого редактирования полной структуры блока.

Что доступно в визуальном режиме:

- поле заголовка;
- rich-text поле TipTap для текста (жирный, курсив, H2/H3, маркированный и нумерованный списки, цитата, ссылка);
- для `text_image` — выбор изображения из Media Library (`MediaPicker`, с загрузкой нового файла прямо из окна выбора) и заполнение `alt`;
- в TipTap кнопка «Загрузить» сохраняет файл в медиатеку, кнопка «Медиатека» вставляет изображение из библиотеки.
- набор в rich-text поле выполняется в стандартном режиме слева-направо (LTR);
- при наборе в rich-text каретка смещается вправо, без «залипания» в начале строки;
- сохранённый текст блока подгружается сразу при первом открытии модального редактора.
- HTML форматирования сохраняется в `content.text` и не требует изменений Content API.

Рекомендация для операторов: использовать `Визуально` как основной режим, а `JSON` — только если нужно добавить нестандартные поля, которых нет в форме.

## Page Builder и legacy-редактор

В админке сейчас существуют два интерфейса редактирования блоков:

- `Page Builder` (`/admin/pages/{id}/builder`) — основной интерфейс для структурированной работы с блоками;
- legacy-редактор (`/admin/pages`, модалка `Редактор блоков`) — fallback/экспертный режим с прямым JSON.

Для блока `Слайдер` доступны пресеты в обоих интерфейсах:

- в builder: кнопки пресетов в `SliderEditor`;
- в legacy: секция `Пресеты слайдера` внутри модалки редактирования блока.

## Content API

API пока предназначен для будущего Vue-интерфейса админки. Он работает через текущую admin-сессию Symfony Security.

Доступные сценарии:

- создать страницу;
- обновить страницу;
- опубликовать страницу;
- архивировать страницу;
- добавить блок;
- обновить блок;
- пересортировать блоки;
- удалить блок.
- получить preview-ссылку для черновика.

Основные endpoints:

- `POST /admin/api/content/pages`
- `PUT /admin/api/content/pages/{id}`
- `POST /admin/api/content/pages/{id}/publish`
- `POST /admin/api/content/pages/{id}/archive`
- `GET /admin/api/content/pages/{id}/preview-link`
- `POST /admin/api/content/pages/{pageId}/blocks`
- `PUT /admin/api/content/blocks/{id}`
- `POST /admin/api/content/pages/{pageId}/blocks/reorder`
- `DELETE /admin/api/content/blocks/{id}`

## Media, Menu и Lead API

Новые launch-ready разделы используют текущую admin-сессию и CSRF-защиту:

- `GET|POST /admin/api/media/assets` (список с `page`, `perPage`, `q`, `type`, `sort` и `pagination` в ответе), `PATCH|DELETE /admin/api/media/assets/{id}`;
- `GET|POST /admin/api/menu/items`, `PUT|DELETE /admin/api/menu/items/{id}`;
- Lead CRM: `GET /admin/api/leads` (пагинация, поиск, фильтры, сортировка), `/summary`, `/assignees`, `/export`, `GET /admin/api/leads/{id}`, `PATCH /{id}/status`, `PATCH /{id}/assignee`, `POST /{id}/notes` — подробности в [admin/crm-leads](admin/crm-leads.md).

Публичные заявки отправляются в `POST /api/leads` с обязательным `consent=true` и honeypot-полем `website`.

## SEO-панель (`/admin/seo`)

Раздел нужен, чтобы при ручном переносе страниц со старого сайта не потерять позиции в поиске. Доступен ролям с правом `seo.edit`. Вкладка выбирается параметром `?tab=` (`robots`, `not-found`, `audit`), поэтому на неё можно дать ссылку.

### Редиректы

- Таблица с поиском по старому и новому URL, фильтром «все / активные / отключённые», сортировкой и постраничной навигацией. Переключатель в строке включает и отключает правило без удаления.
- «Добавить редирект»: старый URL указывается путём без домена (`/old-page/`), новый — путём или полным `https://`-адресом. Кириллицу можно вводить как есть. Для постоянного переезда выбирайте 301.
- Панель не даёт создать редирект на самого себя, на `/admin`, с URL с параметрами `?`/`#`, дубликат источника и цикл. Цепочки (`A → B → C`) разрешены, но после сохранения показывается предупреждение: лучше сразу вести на конечный URL.
- «Проверить все активные редиректы» ищет циклы и цепочки по всей карте и предлагает исправление в один клик.
- «Экспорт CSV» выгружает всю карту; «Импорт CSV» принимает файл или вставленный текст. Сначала нажмите «Проверить»: вы увидите, сколько правил будет создано, обновлено и пропущено, а также ошибки по номерам строк (отчёт можно скачать). «Применить импорт» записывает только корректные строки.

Формат CSV:

```csv
source,target,status,active
/old-fences/,/fences/,301,1
/старые-ворота/,/gates/,301,1
```

Колонки `status` (по умолчанию 301) и `active` (по умолчанию 1) необязательны. Шаблон можно скачать в окне импорта.

### robots.txt

- Редактор с серверной проверкой синтаксиса: ошибки (с номером строки) блокируют сохранение, предупреждения — только подсказки.
- Пустое содержимое означает стандартный файл. Кнопка «Подставить стандартный шаблон» вставляет его в редактор для правки, «Сбросить к стандартному» удаляет собственную версию.
- На staging и других не-production окружениях роботам всегда отдаётся `Disallow: /` — панель показывает об этом заметку; сохранённое содержимое вступит в силу на production.

### Журнал 404

- Показывает адреса, которые запрашивали на публичной части сайта и не нашли: число обращений, последнее обращение, источник перехода. Параметры запроса не хранятся.
- «Создать редирект» открывает форму с готовым старым URL; адреса, для которых правило уже есть, помечены.
- «Очистить старше 90 дней» и «Очистить всё» удаляют записи после подтверждения. Автоочистка: `php bin/console app:seo:not-found:prune --days=90`.

### SEO-аудит

Вкладка использует тот же аудит, что блокирует публикацию страницы: для каждой страницы можно запустить проверку и увидеть замечания P0/P1/P2 (title, description, OpenGraph, контентные блоки), открыть страницу для исправления или проверить сразу все опубликованные.

## Release readiness

Перед выкладкой:

- `make quality` должен проходить локально или в CI;
- `php bin/console app:smoke:test --env=prod` должен проходить на целевом окружении;
- после restore rehearsal проверяются sitemap, login, preview links, Media Library и публичная lead-форма.

## Пользователи, роли и пароли

### Первый администратор (консоль)

Первый администратор создаётся командой (подробности — [33-local-development](33-local-development.md#создание-администратора)):

```bash
php bin/console app:user:create-admin admin@example.com
```

Пароль вводится скрыто; для неинтерактивного запуска используйте переменную окружения `ADMIN_PASSWORD`. Команда идемпотентна: повторный запуск для существующего пользователя ничего не меняет. Сброс пароля: `app:user:create-admin <email> --reset-password` или `app:user:change-password <email>`. Роль суперадминистратора: `--super`.

### Раздел «Пользователи и роли» (`/admin/users`)

Доступен ролям `ROLE_ADMIN` и `ROLE_SUPER_ADMIN` (право `users.manage`). Возможности:

- создать пользователя: email, начальный пароль (не менее 12 символов), роль. Пароль передаёте пользователю по защищённому каналу и просите сменить его после первого входа; отправки ссылки по почте пока нет;
- сменить роль: допустимы только `ROLE_SUPER_ADMIN`, `ROLE_ADMIN`, `ROLE_EDITOR`, `ROLE_SEO`, `ROLE_MANAGER`, любые другие значения отклоняются (422);
- сбросить пароль другому пользователю и сменить собственный пароль (нужен текущий пароль). После смены или сброса пароля все сессии этого пользователя (включая текущую при смене собственного пароля) перестают действовать и требуют повторного входа;
- деактивировать/активировать и удалить пользователя.

Назначать и снимать `ROLE_SUPER_ADMIN` может только суперадминистратор.

### Защита от потери доступа

Сервер отклоняет (HTTP 409, коды в поле `code`) операции, после которых администраторы остались бы без доступа:

- `SELF_LOCKOUT` — снять с себя `ROLE_ADMIN`/`ROLE_SUPER_ADMIN`, деактивировать или удалить собственную учётную запись;
- `LAST_ADMIN` — снять роль, деактивировать или удалить последнего активного администратора (или последнего суперадминистратора);
- `ROLE_NOT_ALLOWED` (HTTP 403) — назначение или снятие `ROLE_SUPER_ADMIN` не суперадминистратором.

Если доступ всё же потерян, восстановите его консолью: `app:user:create-admin <email> --reset-password`.

### Журнал аудита

Создание, изменение ролей/активности/пароля и удаление пользователей попадают в журнал (`Системный центр → Аудит`) с типом сущности `AdminUser`. Хеш пароля и сам пароль в журнал не записываются: при смене пароля фиксируется только `password: [redacted]`. Действия из консоли помечаются как `console`.

> Примечание: сейчас `AdminUser::getRoles()` всегда добавляет `ROLE_ADMIN` (вход в `/admin` требует `ROLE_ADMIN`). Вход для `ROLE_EDITOR`/`ROLE_SEO`/`ROLE_MANAGER` без прав администратора появится отдельным изменением (A2).
